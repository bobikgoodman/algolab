Массивы и сортировка

Инвентарь, таблица рекордов, список квестов — это массив. Почти любой экран со списком в игре — массив объектов, отсортированный по ключу.

  1. Класс — шаблон предмета: какие у него есть поля (имя, редкость, цена, количество). Объект — конкретный предмет, созданный по шаблону.
  2. Список хранит объекты по порядку, у каждого номер с нуля — его видно в углу карточки.
  3. Сортируем не «предметы», а по их полю — ключу.
  4. Два ключа: сначала главный, при равенстве — второй. Нажми «Редкость» и посмотри, как выстроятся три обычных предмета.
  5. Сортировку руками не пишем. Задача программиста — правильно задать ключ.
  6. Не сортируем каждый кадр в Update(): только когда список изменился.

Python-код меняется вместе с инвентарём, а в конце страницы — тот же код на C# для Unity.

Графы и обход в ширину

Карта из клеток — это граф: проходимая клетка — вершина, соседние клетки связаны ребром. BFS идёт от старта волной: сначала все клетки на расстоянии 1, потом 2, потом 3.

  1. Очередь: кто пришёл первым, тот первым и обрабатывается.
  2. Посещённые: клетку записываем один раз — иначе волна бегает по кругу и игра зависает.
  3. Волна приходит в клетку впервые по самому короткому пути, поэтому BFS даёт кратчайший путь.
  4. Путь восстанавливаем с конца: от выхода в соседа с числом на 1 меньше.
  5. Проверка софтлока: если BFS нашёл не все свободные клетки, на карте есть отрезанная область.

Переключи режим на «стек (DFS)»: путь найдётся, но не кратчайший. Это частая ошибка.

Вероятности и лут

Дроп, крит, случайное событие держатся на двух идеях: взвешенный рандом и «шанс хотя бы раз».

  1. Взвешенный рандом — линейка из отрезков длиной с вес. Бросаем случайную точку: куда попала, то и выпало.
  2. Шанс = вес / сумма весов. Добавили предмет — шансы остальных упали.
  3. «Хотя бы раз» не складывается: 10 × 5% ≠ 50%. Считаем 1 − (1 − p)ⁿ.
  4. Pity-гарант: после N неудач редкий предмет выпадает точно, чтобы невезучий игрок не бросил игру.
  5. Псевдорандом (PRD): шанс растёт с каждой неудачей — C, 2C, 3C… и сбрасывается после срабатывания. Средний шанс тот же, но без длинных серий удачи и неудачи. Так работают криты и оглушения в Dota 2.
  6. В Python random.randrange(100) даёт числа от 0 до 99, а random.randint(1, 6) — от 1 до 6 включительно. В Unity Random.Range(0, 100) для целых тоже не включает 100.
Задачи

1. Новый предмет

Веса 70 / 25 / 5. Добавили эпический с весом 10. Шанс легендарки?

Ответ

5 / 110 ≈ 4,5% (было 5%). Нажми «+ Эпический» и проверь.

2. Десять сундуков

Шанс легендарки 5%. Вероятность получить её хотя бы раз за 10 сундуков?

Ответ

≈ 40%: 1 − 0,95¹⁰ ≈ 1 − 0,599. Значит, 60% игроков останутся ни с чем.

3. Сколько ждать

Сколько сундуков в среднем до первой легендарки при 5%?

Ответ

20 (1 / 0,05). Но «в среднем» не значит «точно»: открой 1000 сундуков и посмотри на самую длинную серию неудач.

4. Гарант 90%

Сколько сундуков нужно, чтобы шанс хотя бы одной легендарки был не меньше 90%?

Ответ

45. 0,95⁴⁴ ≈ 0,105, 0,95⁴⁵ ≈ 0,099. Проверь в калькуляторе ниже.

5. Псевдорандом

Крит 25% на PRD, C ≈ 8,5%. Какой шанс крита на 3-й атаке после последнего крита? Сколько атак подряд максимум можно пройти без крита?

Ответ

≈ 25,4% (3 × 8,47%). На 12-й атаке шанс 12 × 8,47% ≥ 100%, поэтому без крита — максимум 11 атак. Проверь на слайде 7.

Сцены и префабы

Сцена — отдельный экран игры: загрузка, меню, сам уровень. Префаб — сохранённый шаблон объекта, из которого Unity делает копии на сцене.

  1. Сцены делим по экранам: Boot (менеджеры), MainMenu, Game. Уровни — отдельные сцены или префабы, которые загружаются в Game.
  2. Префаб — как класс из занятия 1: шаблон. Копии на сцене — экземпляры. Поменял префаб — поменялись все копии.
  3. Override — правка у одной копии. Unity помечает её синей полоской. Её можно применить к префабу (Apply) или откатить (Revert).
  4. Prefab Variant — наследник: «Гоблин-лучник» сделан из «Гоблина» и хранит только отличия.
  5. Вложенные префабы: Игрок = Тело + Меч + Полоска здоровья. Каждую часть правят отдельно.
  6. Файл сцены хранит только отличия экземпляров от префаба. Чем меньше правок прямо на сцене, тем меньше конфликтов в команде.
  7. Правило команды: одну сцену правит один человек. Остальные работают в своих префабах и в личных сценах-песочницах.
Задачи

1. Сколько поменяется?

На сцене 12 гоблинов из одного префаба. У двух на сцене изменено здоровье. В префабе меняем скорость с 2 на 3. У скольких гоблинов скорость станет 3? А если в префабе поменять здоровье?

Ответ

Скорость — у всех 12: overrides были на здоровье, а не на скорости. Здоровье — у 10: у двух останется своё значение. Проверь в конструкторе ниже.

2. Как разложить проект?

Игра: меню, три уровня и магазин между уровнями. Какие сцены и какие префабы ты сделаешь?

Ответ

Один из хороших вариантов: сцены Boot, MainMenu, Game. Уровни — префабы Level_1…Level_3, которые загружаются в Game. Магазин — UI-префаб поверх Game. Префабы: Player, Enemy и его варианты, Coin, HUD, ShopPanel.

3. Кто где работает?

Команда из четырёх человек делает один уровень. Как не поругаться из-за сцены Game?

Ответ

Сцену Game правит один человек. Остальные делают свои префабы: уровень, врагов, интерфейс — и проверяют их в личных сценах Sandbox_Имя. В Game попадают уже готовые префабы.

ScriptableObject: данные отдельно

ScriptableObject — файл-ассет с данными, который лежит в папке проекта, а не на сцене. Код говорит, как гоблин ходит, а ассет — сколько у него здоровья.

  1. Создаётся через меню Create благодаря атрибуту [CreateAssetMenu].
  2. Один ассет — много пользователей: 50 гоблинов ссылаются на один GoblinData, а не хранят 50 копий чисел.
  3. Баланс правится в одном месте, без кода и без сцен. Геймдизайнер не мешает программисту.
  4. Ассет — отдельный текстовый файл: его правки почти не конфликтуют со сценами.
  5. Типичные ScriptableObject: враги, оружие, предметы, уровни, волны, таблицы лута, настройки сложности.
  6. Ловушка: в редакторе изменения ассета в Play Mode не откатываются после остановки игры.
  7. ScriptableObject — для данных игры, а не для прогресса игрока: в собранной игре он не сохраняется между запусками.
Задачи

1. Где хранить?

Максимальное здоровье гоблина, текущее здоровье конкретного гоблина, цена меча в магазине, сколько монет у игрока сейчас. Что из этого — в ScriptableObject?

Ответ

В ScriptableObject: максимальное здоровье и цена меча — это неизменные данные игры. Текущее здоровье живёт в компоненте на объекте, монеты игрока — в сохранении.

2. Баланс

Урон гоблина записан числом в трёх скриптах и ещё изменён на двух сценах. Нужно поднять его на 20%. Сколько мест править сейчас и сколько с ScriptableObject?

Ответ

Сейчас пять мест, и одно легко забыть. С ScriptableObject — одно: поле damage в ассете GoblinData.

3. Ловушка Play Mode

Для теста в Play Mode поставил гоблину здоровье 999 в ассете и остановил игру. Что будет со значением?

Ответ

Останется 999. Изменения ScriptableObject в редакторе сохраняются в файл. Верни руками или меняй копию: Instantiate(data).

Менеджер, состояния и события

GameManager знает, в каком состоянии сейчас игра, и переключает её. События развязывают скрипты: враг объявляет «я погиб», а кому надо — подписываются.

  1. Состояния: Menu, Playing, Paused, GameOver, Victory. В каждый момент ровно одно.
  2. Разрешены не все переходы: из меню нельзя на паузу, из паузы нельзя проиграть.
  3. У состояния есть вход и выход: вошли в Paused — Time.timeScale = 0 и показали меню паузы, вышли — вернули 1.
  4. GameManager один на всю игру и живёт между сценами: DontDestroyOnLoad.
  5. Связанность: если враг сам вызывает счёт, звук и достижения, удаление любого из них ломает врага.
  6. Событие: враг вызывает GameEvents.RaiseEnemyDied() и не знает, кто слушает. Добавить квесты — значит подписать их, врага не трогаем.
  7. Подписка в OnEnable, отписка в OnDisable. Иначе событие позовёт уже уничтоженный объект.
Задачи

1. Запрещённые переходы

Какие переходы ошибочны: Menu→Playing, Menu→Paused, Playing→Paused, Paused→GameOver, GameOver→Menu, Paused→Playing?

Ответ

Menu→Paused — ставить на паузу нечего. Paused→GameOver — на паузе время стоит, проиграть нельзя. Проверь на пульте ниже.

2. Добавляем квесты

Враг при смерти напрямую вызывает четыре системы. Нужно добавить квесты. Что придётся менять при прямых вызовах и что — с событием?

Ответ

Прямые вызовы: правим Enemy.cs, и он зависит уже от пяти систем. С событием: Enemy не трогаем, квесты сами подписываются на OnEnemyDied.

3. Забыли отписаться

Счёт подписался в OnEnable, не отписался, а при смене сцены его объект уничтожили. Что случится при следующей смерти врага?

Ответ

Ошибка MissingReferenceException, и подписчики после него в списке не получат событие. Лечится отпиской в OnDisable.

Core loop и мета-прогрессия

Core loop — действие, которое игрок повторяет снова и снова. Мета-прогрессия — то, что остаётся после забега: валюта, прокачка, открытые уровни.

  1. Core loop длится секунды или минуты: бой → лут → улучшение → снова бой.
  2. Мета-цикл медленнее: забег → награда → прокачка в лагере → новый забег, уже сильнее.
  3. Всё в памяти исчезает при закрытии игры. Мета-прогрессию нужно сохранять в файл.
  4. Сохраняем только прогресс: монеты, уровни прокачки, открытые уровни, рекорды. Не объекты сцены и не данные из ScriptableObject.
  5. Как: класс SaveData → JsonUtility.ToJson → файл в Application.persistentDataPath. Загрузка — обратно через FromJson.
  6. Когда: конец забега, покупка, выход из игры. Не в Update.
  7. Нет файла — новая игра. Поле version спасает, когда формат сохранения меняется.
  8. По анонсу занятия, работающий core loop с сохранением прогресса — базовый уровень ТЗ на 30 баллов.
Задачи

1. Что сохранять?

Монеты, позиции врагов в текущем забеге, уровень прокачки меча, максимальное здоровье гоблина, открытые уровни, громкость звука.

Ответ

В сохранение прогресса: монеты, прокачка меча, открытые уровни. Громкость — в настройки (PlayerPrefs). Позиции врагов не храним: забег начнётся заново. Здоровье гоблина лежит в ScriptableObject.

2. Когда сохранять?

Назови моменты, когда игра должна записать прогресс, и момент, когда точно не должна.

Ответ

Записываем: конец забега, покупка улучшения, открытие уровня, выход в меню и закрытие игры. Не записываем в Update — это 60 записей на диск в секунду.

3. Новое поле

В обновлении добавили в SaveData поле gems. У игрока старое сохранение без него. Что будет при загрузке?

Ответ

Игра не упадёт: gems получит значение по умолчанию, 0. Но если поле переименовать, старые данные потеряются. Поэтому храним version и переносим данные вручную.

Pull request и код-ревью

Pull request — запрос «влей мою ветку в main». Код-ревью — чтение чужих изменений до слияния, чтобы правки разных участников не ломали проект.

  1. main всегда запускается и играется. Напрямую в main не пушим.
  2. Одна задача — одна ветка: feature/inventory, fix/pause.
  3. В PR видно diff: что добавлено (+) и удалено (−). Описание: что сделано и как проверить.
  4. Ревьюер оставляет комментарии к строкам и выбирает: Approve или Request changes.
  5. Маленькие PR проверяются быстрее и лучше. Ориентир — до 200–300 строк.
  6. Конфликт — двое поменяли одни и те же строки. Сцены конфликтуют хуже всего.
  7. Unity в git: .gitignore для Library и Temp, Asset Serialization = Force Text, файлы .meta коммитим всегда.
Чек-лист ревьюера
Задачи

1. Что не так с PR?

В PR изменено 47 файлов: 3 скрипта, сцена Game и папка Library.

Ответ

Library не должна попадать в git — её добавляют в .gitignore. Правку сцены Game согласовать с её владельцем. Остаются 3 скрипта — их и проверяем.

2. Будет ли конфликт?

Аня и Боря поменяли разные методы в одном файле Player.cs.

Ответ

Обычно нет: git сам сливает разные участки файла. Конфликт будет, если поменять одни и те же строки.

3. Порядок

Расставь: открыть PR, слить в main, создать ветку, ревью, коммиты, исправить замечания, подтянуть свежий main.

Ответ

Создать ветку → коммиты → открыть PR → ревью → исправить замечания → слить в main → подтянуть свежий main.
